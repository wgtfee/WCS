## 3. 测试范围

### 3.1 单场景规模递增

使用相同结构的确定性场景，逐步提高任务和车辆数量：

```text
100 任务 / 5 车辆
500 任务 / 10 车辆
1000 任务 / 20 车辆
2500 任务 / 30 车辆
5000 任务 / 50 车辆
```

每个任务包含：

- 来源节点和目标节点；
- 目标站点；
- 两个交通资源；
- 基础优先级和生产订单优先级；
- 可选交期；
- 预计行驶时间；
- 作业时间；
- EMS 车辆类型约束。

### 3.2 并发仿真

并发执行 8 个场景，每个场景：

```text

```

总计 8000 个仿真任务。

### 3.3 策略 A/B

- BaselineDynamicPriority
- AgingFirst

### 4.1 结论

- 5000 任务场景在 4 核 Windows Runner 上低于 0.6 秒完成；
- 所有规模均为 100% 完成、0 异常；
- 计算速度最低约 6061 任务/s；
- 5000 任务运行工作集约 137.48 MB；
- 仿真计算 CPU 性能明显高于工业现场实际任务产生速度，仿真内核本身不是典型现场吞吐瓶颈。

### 4.2 注意事项

本次每个规模只执行一轮正式测量，2500 与 5000 任务的每任务耗时存在 JIT、GC 和运行器抖动影响。若用于正式硬件选型，应至少重复 10 次并使用中位数和 P95，而不是使用单次最快或最慢结果。


### 7.2 发现的容量口径缺陷

当前 `BuildStressScenario` 将任务到达时间分布到：

```text
0 ～ HorizonSeconds - 1
```

最后几秒到达的任务仍需要：

- 20～40 秒行驶；
- 5～10 秒服务；
- 可能的站点和路权等待。

这些任务在仿真窗口结束前天然无法完成。`BuildMetrics` 会把所有未完成任务计入 `FailedTaskCount`，而容量点的 Sustainable 判定要求：

```text
P95 <= 120 秒
交期违约率 <= 5%
所有重复运行 FailedTaskCount == 0
```

因此即使 `20 台车辆 / 900 任务每小时` 的 P95 只有 4.5 秒、交期违约为 0，也会因为窗口尾部任务未完成而判定为不可持续。

### 7.3 结论

当前容量基线的：

```text
MaximumSustainableTaskRatePerHour
RecommendedVehicleCount
```

不能直接用于现场选车或设备能力承诺。

建议采用以下任一修正：

1. **到达截止窗口**：最后一个任务最迟在 `Horizon - MaximumCycleSeconds` 到达；
2. **排空窗口**：任务到达窗口结束后继续仿真一段 Drain 时间，但吞吐分母仍使用任务到达窗口；
3. **观测截断**：只评价在截止时间前具备完整完成机会的任务；
4. 同时分别报告 `Arrived`、`Completed`、`InFlightAtCutoff` 和 `FailedByFault`，不要把窗口内未完成与真实失败混为一类。

在修正前，本报告只认可容量点的吞吐、P95、交期和利用率原始数据，不认可 Sustainable 最终布尔值。

## 10. 最终结论

第十二阶段离散事件仿真内核在 4 核 Windows Runner 上具备明显余量：

```text
5000 任务单场景 < 0.6 秒
8 路并发 8000 任务 < 0.3 秒
无异常
```

因此对典型工业现场的离线回放、策略比较和批量优化，计算能力不是主要瓶颈。

当前最重要的问题不是计算速度，而是容量基线的尾部任务统计口径。修正该口径并使用真实历史数据重新运行后，才能形成可信的最大持续任务率和推荐车辆数量。
