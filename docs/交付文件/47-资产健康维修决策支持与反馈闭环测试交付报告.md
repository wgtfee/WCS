## 3. Core 测试

`AssetHealthMaintenanceDecisionEngineTests` 覆盖：

1. Confirmed 根因生成检查建议；
2. Pending 和 Rejected 不生成建议；
3. 无已审批规则时不生成伪建议；
4. 相同规则、分析和事件版本生成相同 RecommendationId；
5. Supplemented 根因可匹配精确节点规则；
6. Confirmed 置信度低于门槛时拒绝；
7. 精确 RootCauseNodeId 规则优先于 RootCauseKind 规则；
8. Enabled 规则集必须包含版本、来源和审批信息。

专项编译工作流：`.github/workflows/anomaly-maintenance-compile.yml`。

## 4. SQL 对象与断言

### 4.1 RuleSetVersion

- Version 唯一；
- RuleSetHash 唯一；
- 同 Version 不同 Hash 拒绝；
- 保存来源和审批信息。

### 4.2 Recommendation

- RecommendationId 唯一；
- 重复生成只保留一条；
- 原始 RecommendationJson 不被反馈覆盖；
- 当前状态和工单摘要可查询。

### 4.3 FeedbackJournal

- FeedbackId 唯一；
- Accepted 和 Repaired 独立保存；
- 重复 FeedbackId 不新增 Journal；
- Actor、工单号、处理人、分数和备注可追溯。

### 4.4 TrainingLabel

- Repaired 生成 `fault-confirmed`；
- 初始状态 PendingApproval；
- 人工 Approved/Rejected；
- 不调用模型训练或激活接口。

## 6. API 验收

- 状态接口返回 Runtime、Store、Metrics；
- 规则接口返回版本、Hash、置信度门槛和规则；
- 建议支持状态和资产过滤；
- 反馈需要 Actor；
- Rejected、FalsePositive、NoFaultFound 必须填写备注；
- PostHealthScore 限制在 0～100；
- 标签复核不允许回写 PendingApproval；
- LoadTest 接口在非 LoadTest 环境返回 404。

## 7. 幂等与恢复

幂等键：RuleSet Version、RuleSetHash、RecommendationId、FeedbackId、TrainingLabel CandidateId。

Host 重启后通过 SQL 恢复建议生命周期、最新反馈摘要、完整 Feedback Journal 和标签审批状态。

## 8. 指标验证

专项验证：总建议 1、接受建议 1、完成建议 1、维修确认 1、误报 0、接受率 100%、确认故障率 100%、误报率 0%。这些数字只用于确定性测试，不代表现场业务质量基线。

## 9. 安全边界测试

必须保持：

- `AssetHealthMaintenance.Enabled=false` 为仓库和 Production 默认；
- Production RuleSet Version、Source、审批信息为空且 `Rules=[]`；
- 无审批信息、无已复核根因或无匹配规则时不生成建议；
- MES 工单只作为审计元数据；
- 反馈不覆盖 RecommendationJson、v3.5 事件或 v3.6 分析；
- 标签 Approved 不自动训练、激活或替换模型；
- 无 PLC 写入、设备停止、任务取消、路线、路权、车辆选择或派单修改；
- SQL 失败不阻塞控制链路。
