# EMS/RGV 数据模型与数据库设计说明书

## 1. 目的

本文说明统一调度运行模型、SQL 持久化模型、Journal 分类、主键与唯一性、版本控制、恢复和数据保留要求。

## 2. 数据分层

| 层次 | 用途 | 特性 |
|---|---|---|
| 运行时内存模型 | 实时调度、状态机和路权 | 低延迟、单一事实源 |
| 专用 SQL 表 | 车辆、任务、路权、命令、配置、点位、治理、联调 | 可查询、可恢复、结构化约束 |
| Transport Journal | 趋势、决策、健康、快照、备份、演练、仿真 | 分类扩展、JSON 载荷 |
| 文件备份 | 离线逻辑备份 | SHA-256、不可覆盖、可下载 |

## 3. 运行时核心模型

### 3.1 TransportVehicleSnapshot

| 字段 | 说明 |
|---|---|
| VehicleId | 车辆唯一编号 |
| Kind | EMS/RGV |
| State | 车辆状态 |
| CurrentNodeId | 最后可信节点 |
| IsOnline | 在线状态 |
| BatteryPercent | 电量 |
| Capabilities | 能力集合 |
| ActiveTaskCount | 活动任务数 |
| Version | 单调递增版本 |
| UpdatedAtUtc | 更新时间 |

### 3.2 TransportDispatchAssignment

包含 RequestId、VehicleId、取货路径、载货路径、ReservationId、创建时间和不可变派单结果。

### 3.3 TransportExecutionSnapshot

包含执行阶段、车辆、起点、目标、可信节点、反馈序号、装载状态、暂停/故障原因和更新时间。

### 3.4 RouteReservation

包含预留编号、所有者、资源列表、租约、到期时间、物理占用和确认时间。

### 3.5 TransportCommandRecord

包含命令编号、RequestId、车辆、命令类型、序号、状态、发送/确认/完成时间、错误和重试信息。

## 4. 专用持久化对象

### 4.1 Transport Runtime State

用于持久化：

- 车辆快照；
- 执行快照；
- 活动路权；
- 命令记录。

要求：

- 以业务 ID 唯一；
- Upsert 不得生成重复活动记录；
- JSON 序列化字段必须保留 Schema 兼容；
- 保存时间统一使用 UTC。

### 4.2 Transport Configuration

保存运行配置及版本。配置包含车辆定义、驱动端点、交通资源、充电站和策略。

要求：

- `ConfigurationId` 唯一；
- `Version` 乐观锁；
- `UpdatedBy` 和 `UpdatedAtUtc` 必填；
- 保存成功后才能应用到运行时。

### 4.3 PLC Signal Map

保存每台车辆的点位映射、模式、驱动编号、标签、超时、版本和启用状态。

要求：

- `VehicleId` 唯一；
- DriverId 必须引用有效驱动；
- 真实 PLC 模式的必填标签不能为空；
- 更新采用 ExpectedVersion。

### 4.4 Governance

保存申请、审批、执行和审计记录。

关键约束：

- OperationId 唯一；
- OperationType + TargetId 与执行严格匹配；
- 审批人不得等于申请人；
- BeginExecution 只能成功一次。

### 4.5 Commissioning

保存联调会话、单点读写、通信 Trace、故障码和恢复冲突处置结果。

## 5. Transport Journal

Journal 以 `Category + RecordId` 作为业务 Upsert 键，载荷为 JSON。

### 5.1 分类字典

| 值 | 分类 |
|---:|---|
| 0 | ChargingPlan |
| 1 | TaskReassignment |
| 2 | TrafficIncident |
| 3 | PerformanceSnapshot |
| 4 | DriverState |
| 5 | ProductionTuning |
| 6 | ProductionStation |
| 7 | SingleTrackSection |
| 8 | ProductionTrend |
| 9 | DispatchDecision |
| 10 | ProductionQueue |
| 11 | ConsistencyReport |
| 12 | ConfigurationSnapshot |
| 13 | ObservabilityHealth |
| 14 | ProductionReadiness |
| 15 | OperationalBaseline |
| 16 | LogicalBackup |
| 17 | RecoveryDrill |
| 18 | SimulationRun |
| 19 | StrategyComparison |
| 20 | CapacityBenchmark |
| 21 | FinalAcceptanceReport |
| 22 | OptimizationRecommendation |

分类值一旦发布不得重新编号，只能追加。

### 5.2 Journal 字段

- `JournalId`
- `Category`
- `RecordId`
- `PayloadJson`
- `OccurredAtUtc`
- `UpdatedAtUtc`

### 5.3 使用规则

适合 Journal：

- 低频趋势；
- 可变结构报告；
- 版本快照；
- 仿真结果；
- 审计摘要。

不适合 Journal：

- 高频按字段查询；
- 强外键关系；
- 大量并发状态更新；
- 需要数据库唯一约束的活动任务。

## 6. 一致性和版本

### 6.1 UTC

所有持久化时间使用 UTC；Desktop 展示时转换为本地时间。

### 6.2 版本控制

配置、点位和车辆快照使用单调递增版本。保存接口必须带 ExpectedVersion。

### 6.3 三方一致性

比较对象：

```text
SQL 持久化状态
↔ 运行时内存状态
↔ PLC/控制器诊断状态
```

差异只记录和报警，不自动覆盖。

## 7. 恢复读取顺序

1. 读取运行配置；
2. 读取 PLC 点位映射；
3. 恢复车辆、执行、路权和命令；
4. 恢复生产整定、站点和单轨定义；
5. 恢复生产队列与决策帧；
6. 恢复可观测性、韧性和仿真历史；
7. 读取 PLC 当前状态；
8. 运行一致性巡检。

## 8. 数据保留

建议基线：

| 数据 | 建议保留 |
|---|---|
| 活动运行状态 | 始终保留最新 |
| 命令历史 | 90～180 天或按项目要求 |
| 通信 Trace | 7～30 天 |
| 审计记录 | 不少于 1 年 |
| 生产趋势 | 6～12 个月 |
| 配置快照 | 最近 100 份并保留发布节点 |
| 逻辑备份 | 默认 48 份，可按容量调整 |
| 仿真/容量/验收报告 | 项目全生命周期 |

实际清理策略必须形成项目附件，禁止直接删除活动状态和审批审计。

## 9. 备份文件结构

每份备份包含：

```text
manifest.json
payload.json
```

Manifest 保存 BackupId、文件名、SHA-256、大小、SchemaVersion、创建人、原因和时间。Payload 保存配置、点位、状态、Journal 和基线。

备份不可用同一 BackupId 覆盖。

## 10. 数据库变更规则

1. 新增表或字段必须提供向前兼容迁移方案。
2. Journal 枚举只能追加。
3. 删除字段前至少跨一个发布版本保留读取兼容。
4. 生产数据库变更必须在备份后执行。
5. 发布回退必须验证旧版本能读取当前 Schema。
6. 数据库脚本、实体和文档必须同时更新。

## 11. 数据安全

- 连接字符串不得提交真实生产密码；
- 备份目录应限制操作系统权限；
- 备份下载要求认证；
- 审计数据不得由普通操作员删除；
- 现场敏感点位表不应对无权限用户开放；
- 导出报告应脱敏人员标识和项目敏感参数。
