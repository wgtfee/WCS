# EMS/RGV 开发维护与扩展指南

## 1. 适用对象

面向后续维护统一调度、增加设备类型、扩展协议、修改策略或修复问题的研发人员。

## 2. 解决方案结构

```text
Wcs.Core           领域模型、调度、交通、执行、驱动抽象
Wcs.Application    HostedService 和应用注册
Wcs.Infrastructure SQL/File 持久化和配置绑定
Wcs.Host           API、Health、Middleware
Wcs.Desktop        Avalonia UI 和 API 客户端
Wcs.Core.Tests     Core 自动化测试
```

依赖方向应保持：

```text
Host/Application/Infrastructure/Desktop → Core
Core 不依赖 Host、Infrastructure 或 Desktop
```

## 3. 核心目录

```text
src/Wcs.Core/TransportScheduling
src/Wcs.Application/HostedServices
src/Wcs.Host/Controllers
src/Wcs.Infrastructure/Persistence/Services
src/Wcs.Desktop/ViewModels
src/Wcs.Desktop/Views
src/Wcs.Core.Tests
```

## 4. 编码原则

1. 使用不可变 record 表示快照和结果。
2. 活动状态通过服务方法和 CAS 更新。
3. 所有时间使用 UTC。
4. RequestId、CommandId、OperationId 和 SnapshotId 明确区分。
5. 控制层不得直接读取 appsettings 中的现场 PLC 地址。
6. 业务失败优先返回结果对象，非预期程序错误才抛异常。
7. 后台服务单次异常不能终止循环。
8. 物理占用规则必须有单元测试。
9. 新枚举持久化值只能追加，不能重排。
10. 任何仿真/查询功能不得产生隐藏写副作用。

## 5. DI 注册

Core 使用 `TryAddSingleton` 提供默认内存实现。Infrastructure 使用 `Replace` 注入 SQL/File 实现。

装饰器注册时：

- 基础实现使用具体类型；
- 装饰器构造函数依赖具体基础类型；
- 接口最后解析到最外层装饰器；
- 禁止装饰器依赖自身接口造成循环。

## 6. 新增车辆类型

步骤：

1. 在 `TransportVehicleKind` 追加枚举值；
2. 定义车辆能力和状态映射；
3. 实现 `ITransportVehicleDriver`；
4. 必要时实现新的 `ITransportDriverChannel`；
5. 增加点位模板和导入校验；
6. 注册 Driver；
7. 验证车辆选择、派单、命令、恢复和联调；
8. 更新正式文档。

不要复制一套新的 DispatchEngine。

## 7. 新增协议

例如 OPC UA 或厂商 SDK：

1. 实现访问器/Channel；
2. 保持统一命令和诊断模型；
3. 点位/节点映射配置化；
4. 支持批量读取；
5. 保持命令序号相关性；
6. 添加断线、超时、乱序和重启测试；
7. 不在业务服务中引入协议类型。

## 8. 新增交通资源

对电梯、防火门、洁净区门禁等：

- 复用 `TrafficResource` 和路权；或
- 实现 `ITransportDispatchAdmissionPolicy`。

准入策略只决定允许/拒绝和原因，不直接创建执行任务或写 PLC。

## 9. 修改调度策略

生产策略修改流程：

```text
新增/调整策略实现
→ 单元测试
→ 历史回放
→ A/B 对比
→ 容量测试
→ 安全评审
→ 配置审批
→ 小流量上线
```

不得直接修改基础排序后在现场试错。

## 10. 新增 Journal 分类

1. 只在枚举末尾追加值；
2. 定义 Payload record；
3. 确定 RecordId 幂等键；
4. 增加 Load/Restore；
5. 增加序列化兼容测试；
6. 更新数据字典。

## 11. 新增 API

- Controller 只编排，不实现核心算法；
- 写接口必须明确认证和权限；
- 危险操作接入治理；
- 版本冲突返回 409；
- 返回结果包含可解释原因；
- 保留 TraceId；
- 更新 API 文档和 Desktop 客户端。

## 12. 新增 Desktop 页面

1. 创建 ViewModel；
2. 创建 View/axaml.cs；
3. 注册 DI；
4. 增加菜单路由；
5. API 客户端只访问 Host；
6. 高风险按钮不得绕过审批；
7. XAML 使用现有主题资源；
8. Windows CI 构建验证。

## 13. 测试要求

每个修复至少包含：

- 能复现原问题的测试；
- 修复后的通过断言；
- 相关安全回归；
- 旧阶段测试继续通过。

时间异步测试应使用有界条件等待，不使用脆弱固定延迟。

## 14. 并发要求

重点检查：

- 车辆 CAS；
- 路权原子预留；
- 同车命令串行；
- 不同车辆并行；
- 配置乐观锁；
- OperationId 一次执行；
- 容量仿真串行门槛；
- 文件备份原子提交。

## 15. 日志和可观测性

新增关键业务链路时：

- 使用现有 `ITransportTelemetryService`；
- 选择或追加 TraceOperationKind；
- RequestId 跨线程关联；
- 不在高频循环记录大载荷；
- 指标名称保持稳定；
- 监控失败不得阻塞控制。

## 16. 数据兼容

- record 新增字段提供默认值；
- 反序列化旧 Journal 不应失败；
- 删除/重命名字段需提供兼容层；
- SQL 实体变化同步 DatabaseInitializer；
- 回退版本前验证 Schema。

## 17. 发布流程

```text
从 develop 建临时分支
→ 实现和文档
→ 静态审查
→ 快进 develop
→ Windows CI
→ 修复失败
→ 研发验收
```

未经明确要求不修改或合并 `main`。

## 18. 代码评审清单

- 是否改变物理占用语义；
- 是否可能重复下发命令；
- 是否引入查询副作用；
- 是否绕过治理；
- 是否破坏版本兼容；
- 是否新增无界集合/循环；
- 是否在生产线程执行大规模仿真；
- 是否更新测试和文档；
- 是否存在硬编码现场点位；
- 是否保持单活约束。
