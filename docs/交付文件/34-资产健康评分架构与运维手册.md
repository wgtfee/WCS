# AnomalyEngine v3.4 资产健康评分架构与运维手册

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 功能名称 | AnomalyEngine v3.4 — 可解释资产健康评分 |
| 研发分支 | `feature/anomaly-health-scoring-v3-4` |
| 目标分支 | `develop` |
| PR | `#27` |
| 上游依赖 | AnomalyEngine v3.3 多模型异常证据融合 |
| 默认状态 | `AnomalyHealthScoring:Enabled=false` |
| 当前历史 Provider | `Memory` |
| 安全结论 | 只读诊断，不写 PLC、不停止设备、不改变任务、路权或调度决策 |

## 2. 目标与边界

v3.4 将 v3.3 的融合风险快照转换为现场更容易理解的 0～100 健康分，并提供：

- Healthy、Attention、Degraded、Critical 四级健康等级；
- 影响健康分的来源、类别、贡献和扣分解释；
- 单资产评分变化点；
- 有界历史窗口；
- 稳定、改善、恶化趋势；
- 历史仓储状态和容量治理指标；
- 可替换的历史持久化接口边界；
- 只读 HTTP API。

v3.4 不包含：

- PLC 写入；
- 自动停机；
- 自动取消任务、修改路线或调整车辆选择；
- 替代 PLC 联锁或原 AlarmCenter 生命周期；
- 剩余寿命预测；
- 维修建议自动生成；
- SQL/InfluxDB 健康历史 Provider 的正式实现。

## 3. 总体数据流

```text
规则 / 统计 / ML / 同群 / 运输周期异常
→ AnomalyEvidence
→ AnomalyFusionEngine v3.3
→ FusedHealthSnapshot（0～1 风险分、Normal/Observe/Warning/Alarm）
→ AssetHealthScoringService v3.4
→ AssetHealthScoreSnapshot（0～100 健康分、四级等级、扣分因子）
→ AssetHealthScoreSamplingService
→ IAssetHealthScoreHistoryStore
→ 默认 InMemoryAssetHealthScoreHistoryStore
→ 当前分、历史、趋势、仓储状态只读 API
```

评分服务不重新读取 PLC，也不绕过 v3.3 的同来源去重、独立来源门槛和状态滞回。

## 4. 当前评分模型

### 4.1 输入

评分输入为 `FusedHealthSnapshot`：

- `Score`：0～1 融合风险分；
- `Status`：Normal、Observe、Warning、Alarm；
- `IndependentSourceCount`：独立来源数量；
- `Evidence`：每个来源最强活动证据；
- `LastEvaluatedAtUtc`：融合评估时间。

### 4.2 风险到健康分映射

默认使用与 v3.3 门槛一致的分段线性映射：

| 风险区间 | 默认风险范围 | 健康分范围 |
|---|---:|---:|
| Normal 区间 | 0～0.35 | 100～85 |
| Observe 区间 | 0.35～0.65 | 85～70 |
| Warning 区间 | 0.65～0.85 | 70～40 |
| Alarm 区间 | 0.85～1.00 | 40～0 |

风险越高，健康分越低。映射连续，不在门槛处产生无理由跳变。

### 4.3 等级判定

健康分等级默认：

| 等级 | 分数范围 |
|---|---:|
| Healthy | ≥85 |
| Attention | ≥70 且 <85 |
| Degraded | ≥40 且 <70 |
| Critical | <40 |

最终等级同时受 v3.3 正式状态下限约束：

| Fusion 状态 | v3.4 最低严重等级 |
|---|---|
| Normal | Healthy |
| Observe | Attention |
| Warning | Degraded |
| Alarm | Critical |

因此不会出现 Fusion 已正式 Alarm，但健康等级仍显示 Healthy 的矛盾结果。

## 5. 扣分解释

总扣分：

```text
TotalPenalty = 100 - HealthScore
```

评分服务按活动 Evidence 的贡献占比分配总扣分：

```text
FactorPenalty = TotalPenalty × FactorContribution / Sum(SelectedContributions)
```

默认最多返回 10 个主要因素，并按贡献从高到低排序。

每个因素包含：

- Source；
- Category；
- Contribution；
- Penalty；
- Reason。

扣分是解释性分配，不是再次参与风险计算，不会反向改变 v3.3 状态。

## 6. 历史记录策略

### 6.1 记录条件

后台服务按 `SamplingIntervalSeconds` 周期读取当前评分。满足任一条件才写入历史：

1. 资产首次出现；
2. 健康等级发生变化；
3. 健康分绝对变化达到 `MinimumScoreChangeToRecord`；
4. 距离上次记录达到 `MaximumUnchangedIntervalSeconds`，写入周期心跳点。

默认：

```text
采样周期                 10 秒
最小变化记录门槛          1 分
无变化最大记录间隔        300 秒
```

该策略避免每 10 秒对所有资产无差别写入相同数据。

### 6.2 变化点字段

每个 `AssetHealthScorePoint` 保存：

- Sequence；
- AssetId；
- 当前/上一健康分；
- ScoreDelta；
- 当前/上一等级；
- GradeChanged；
- Stable、Improving、Deteriorating；
- FusionRiskScore；
- FusionStatus；
- IndependentSourceCount；
- CalculatedAtUtc；
- RecordedAtUtc；
- Summary。

## 7. 趋势计算

趋势默认取最近 `TrendWindowSize=12` 个已记录变化点。

```text
Delta = LastHealthScore - FirstHealthScore
```

默认方向门槛：

| 条件 | 趋势 |
|---|---|
| Delta ≥ 2 | Improving |
| Delta ≤ -2 | Deteriorating |
| 其他 | Stable |

同时返回：

- 当前健康分；
- 窗口总变化；
- 平均、最小、最大健康分；
- 每小时健康分变化率；
- 样本数量；
- 当前等级；
- 窗口起止时间。

趋势只描述历史变化，不预测未来，也不自动触发控制。

## 8. 容量和保留策略

默认容量：

| 参数 | 默认值 | 作用 |
|---|---:|---|
| MaximumHistoryPerAsset | 720 | 单资产最大历史点数 |
| MaximumTrackedHistoryAssets | 10,000 | 最大历史资产数 |
| HistoryRetentionHours | 24 | 时间保留窗口 |
| MaximumHistoryQueryCount | 1,000 | 单次 API 最大返回点数 |

容量治理规则：

- 单资产超过上限时删除最早变化点；
- 资产数量达到上限时淘汰最久未记录的资产历史；
- 维护周期删除超过保留期的数据；
- 空历史资产从仓储中移除；
- Recorded、Deduplicated、EvictedPoints、EvictedAssets 持续计数。

`MaximumTrackedHistoryAssets` 当前上限为 10,000，与 v3.3 内部单次资产快照查询上限一致。

## 9. 持久化边界

### 9.1 接口

`IAssetHealthScoreHistoryStore` 定义：

- `RecordAsync`；
- `GetHistoryAsync`；
- `GetTrendAsync`；
- `GetStatusAsync`；
- `MaintainAsync`；
- `Provider`。

评分算法、后台采样和 Host API 只依赖该接口。

### 9.2 当前实现

当前注册：

```text
IAssetHealthScoreHistoryStore
→ InMemoryAssetHealthScoreHistoryStore
Provider = Memory
```

重要限制：

- Host 重启后历史评分会丢失；
- 当前实现不写 SQL Server、InfluxDB 或文件；
- 不能把内存历史当作法定审计记录或长期维修档案；
- 需要跨重启历史时，应新增独立 Provider 并完成迁移、容量、失败重试和恢复测试。

### 9.3 后续 Provider 要求

SQL 或时序库 Provider 必须满足：

- AssetId + Sequence 或时间唯一性；
- 幂等写入；
- 批量写入和背压；
- 写入失败不阻塞 PLC、调度或 v3.3 Fusion；
- 保留策略和分区；
- 查询最大范围限制；
- Provider 状态和最后错误；
- 断电、重启和数据库不可用恢复测试；
- 不与 PLC Telemetry 大表无边界混存。

## 10. 核心组件

| 组件 | 责任 |
|---|---|
| AssetHealthScoringModels | 评分、历史、趋势、状态和接口模型 |
| AssetHealthScoringService | 风险映射、等级下限和扣分解释 |
| InMemoryAssetHealthScoreHistoryStore | 变化去重、容量、保留、趋势和状态 |
| AssetHealthScoreSamplingService | 周期采样、记录和维护 |

| AnomalyHealthController | 当前评分、历史和趋势只读 API |

## 11. 配置

```json
{
  "AnomalyHealthScoring": {
    "Enabled": false,
    "HealthyMinimumScore": 85,
    "AttentionMinimumScore": 70,
    "DegradedMinimumScore": 40,
    "MaximumFactors": 10,
    "SamplingIntervalSeconds": 10,
    "MinimumScoreChangeToRecord": 1,
    "MaximumUnchangedIntervalSeconds": 300,
    "MaximumHistoryPerAsset": 720,
    "MaximumTrackedHistoryAssets": 10000,
    "HistoryRetentionHours": 24,
    "TrendWindowSize": 12,
    "TrendChangeThreshold": 2,
    "MaximumHistoryQueryCount": 1000
  }
}
```

| 参数 | 说明 | 约束 |
|---|---|---|
| Enabled | 评分和历史采样总开关 | 默认 false |
| HealthyMinimumScore | Healthy 最低分 | 1～100 |
| AttentionMinimumScore | Attention 最低分 | 不高于 Healthy |
| DegradedMinimumScore | Degraded 最低分 | 不高于 Attention |
| MaximumFactors | 最大解释因素数 | 1～100 |
| SamplingIntervalSeconds | 后台采样周期 | 1～3600 秒 |
| MinimumScoreChangeToRecord | 变化记录门槛 | 0～100 分 |
| MaximumUnchangedIntervalSeconds | 无变化心跳记录周期 | 不小于采样周期 |
| MaximumHistoryPerAsset | 单资产最大变化点 | 2～100,000 |
| MaximumTrackedHistoryAssets | 最大历史资产数 | 100～10,000 |
| HistoryRetentionHours | 历史保留时间 | 1～8,760 小时 |
| TrendWindowSize | 默认趋势窗口点数 | 2～单资产上限 |
| TrendChangeThreshold | 趋势方向变化门槛 | 0～100 分 |
| MaximumHistoryQueryCount | 单次最大查询点数 | 1～单资产上限 |

## 12. API

### 12.1 当前状态

```http
GET /api/anomaly/health/status
```

### 12.2 当前资产评分列表

```http
GET /api/anomaly/health/assets?minimumGrade=Degraded&maxCount=200
```

### 12.3 单资产当前评分

```http
GET /api/anomaly/health/assets/{assetId}
```

### 12.4 历史仓储状态

```http
GET /api/anomaly/health/history/status
```

### 12.5 单资产历史变化点

```http
GET /api/anomaly/health/assets/{assetId}/history?fromUtc=2026-07-27T00:00:00Z&maxCount=200
```

历史按时间正序返回，查询结果为空时返回空数组。

### 12.6 单资产趋势

```http
GET /api/anomaly/health/assets/{assetId}/trend?windowSize=12
```

没有历史时返回 404。

## 13. 启用顺序

```text
保持 AnomalyHealthScoring.Enabled=false 升级
→ 验证 v3.3 Fusion 和原调度功能
→ 测试环境启用 AnomalyFusion
→ 确认资产快照、来源数和状态正确
→ 启用 AnomalyHealthScoring
→ 验证当前评分和扣分解释
→ 验证 Recorded/Deduplicated/Evicted 指标
→ 验证历史容量和保留期
→ 观察完整生产周期
→ 审批配置版本
→ 小范围只读上线
```

v3.4 依赖 v3.3 Fusion。评分开关打开但 Fusion 关闭时，API 可用，但不会产生有效资产评分历史。

## 14. 回退

```text
AnomalyHealthScoring__Enabled=false
→ 重启 Host
→ 验证 AssetHealthScoreSamplingService 未启动
→ 确认 /api/anomaly/health/status 显示 Enabled=false
```

关闭 v3.4 不会关闭 v3.3 Fusion、规则、ML、同群或周期异常检测。

## 15. 监控与告警建议

必须观察：

- TrackedAssets；
- RetainedPoints；
- RecordedPoints；
- DeduplicatedPoints；
- EvictedPoints；
- EvictedAssets；
- SamplingIntervalSeconds；
- Host RSS 和托管存活内存；
- SamplingService 错误日志。

建议告警：

```text
EvictedAssets 持续快速增长
RetainedPoints 长期达到理论容量上限
SamplingService 连续失败
历史 API 查询频繁达到 MaximumHistoryQueryCount
健康分长期下降但没有对应 Evidence 原因
```

## 16. 故障排查

### 16.1 当前评分为空

检查：

- AnomalyHealthScoring.Enabled；
- AnomalyFusion.Enabled；
- Fusion 是否存在 TrackedAssets；
- Evidence 是否已过期或资产已淘汰。

### 16.2 当前评分存在但历史为空

检查：

- Host 是否在启用 v3.4 后重启；
- AssetHealthScoreSamplingService 启动日志；
- SamplingIntervalSeconds；
- 是否刚启用尚未到首次采样；
- 资产是否进入当前 10,000 个采样范围。

### 16.3 历史点过多

检查：

- MinimumScoreChangeToRecord 是否被设为 0；
- MaximumUnchangedIntervalSeconds 是否过小；
- 上游风险是否高频抖动；
- 等级门槛是否频繁跨越。

### 16.4 趋势与直觉不一致

趋势使用“已记录变化点”，不是固定时间等间隔原始点。检查：

- TrendWindowSize；
- TrendChangeThreshold；
- 历史窗口起止时间；
- 是否发生等级变化强制记录；
- 是否因保留期删除早期点。

## 17. 安全和审计

以下变更必须留痕并重新测试：

- 健康等级分数门槛；
- v3.3 风险门槛；
- 变化记录门槛；
- 趋势方向门槛；
- 采样周期；
- 历史容量和保留期；
- 历史 Provider；
- 将健康分接入报警、维护工单或控制决策的任何改动。

将健康分接入自动停止、调度降级或维修决策属于新的安全阶段，不在当前 v3.4 交付范围内。
