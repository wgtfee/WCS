# 资产健康根因关联与异常传播架构运维手册

## 1. 文档定位

本文说明 AnomalyEngine v3.6 如何基于 v3.5 活动健康事件和经过审批的设备依赖图，生成可解释的根因候选与异常传播路径。

v3.6 属于只读诊断层：

- 不写 PLC；
- 不停止设备；
- 不取消任务；
- 不修改车辆选择、路线、闭塞区段、路权或调度结果；
- 不替代 AlarmCenter；
- 人工复核不自动修改活动依赖图；
- SQL 或分析失败不得阻塞健康评分和控制链路。

## 2. 总体数据流

```text
规则 / 统计 / ML / 同群 / 周期异常
                 ↓
v3.3 Evidence Fusion
                 ↓
v3.4 Health Score + SQL History
                 ↓
v3.5 Governed Health Event
                 ↓
读取活动事件 + 已审批依赖图
                 ↓
v3.6 Root Cause Analysis Engine
                 ↓
RootCause / Intermediate / Symptom 路径
                 ↓
SQL 不可变分析快照
                 ↓
人工 Confirmed / Rejected / Supplemented Review Journal
```

后台分析服务仅调用 `IAssetHealthGovernanceService.GetEvents` 读取活动事件。分析结果通过 `IAssetHealthRootCauseAnalysisStore` 写入 SQL Server，与实时控制链路隔离。

## 3. 依赖图模型

### 3.1 节点类型

| 类型 | 说明 |
|---|---|
| Asset | 设备、车辆、输送机等资产 |
| Component | 电机、减速机、传感器组件等部件 |
| Signal | PLC 信号或派生特征 |
| Task | 运输、工艺或执行任务 |
| Station | 工位、站点、上下料点 |
| Segment | 路段、闭塞区段或输送区段 |

`NodeId` 是图内稳定标识；`EntityId` 用于匹配 v3.5 健康事件中的 `AssetId`。一个活动图内 `NodeId` 和 `EntityId` 均必须唯一。

### 3.2 边类型

| 关系 | 典型含义 |
|---|---|
| DependsOn | 下游节点依赖上游节点 |
| Feeds | 上游向下游输送物料、状态或能力 |
| Controls | 上游节点控制下游节点 |
| LocatedAt | 部件或信号位于指定设备/工位关系中 |
| Carries | 车辆、托盘或任务承载对象关系 |

每条边统一使用：

```text
UpstreamNodeId → DownstreamNodeId
```

方向表示“潜在原因向潜在结果传播”。`Weight` 范围为 `(0, 1]`，表示该关系用于诊断传播时的可信权重，不表示安全联锁等级。

## 4. 图版本、来源和审批

启用 v3.6 时必须提供：

- `Graph.Version`；
- `Graph.Source`；
- `Graph.ApprovedBy`；
- `Graph.ApprovedAtUtc`；
- 完整 Nodes 和 Edges。

系统对排序后的节点、边、关系、权重和审批元数据计算 SHA-256 `GraphHash`。

SQL 表 `Wcs_AssetHealthRootCauseGraphVersion` 保存：

- Version；
- GraphHash；
- Source；
- ApprovedBy / ApprovedAtUtc；
- 节点数和边数；
- 完整 GraphJson；
- RegisteredAtUtc。

同一 Version 再次注册但 Hash 不同会被拒绝，防止在不升级版本号的情况下静默修改现场拓扑。

## 5. 图校验

启动时执行：

1. 节点和边容量检查；
2. NodeId、EntityId、EdgeId 唯一检查；
3. 边引用节点存在检查；
4. 自环检查；
5. RelationType 和 Weight 检查；
6. 审批元数据检查；
7. `AllowCycles=false` 时使用拓扑排序检测环路。

生产默认 `AllowCycles=false`。只有现场确有循环工艺或回流路线、且已明确诊断方向时才能启用环路；即使允许环路，遍历仍受 `MaximumPropagationDepth` 和 visited 集限制。

## 6. 时间关联

每次分析以一个活动健康事件为 Trigger，选取满足以下条件的活动事件：

```text
事件 LastObservedUtc >= Trigger.FirstDetectedUtc - CorrelationWindow
并且
事件 FirstDetectedUtc <= Trigger.LastObservedUtc + CorrelationWindow
```

然后：

- 按 EventId 去重，保留最高 Version；
- Trigger 优先保留；
- 总数受 `MaximumEventsPerAnalysis` 限制；
- 无图节点映射的事件不会参与图推断，但原健康事件仍保留在 v3.5 Journal 中。

## 7. 根因候选生成

候选集合由以下节点构成：

- 已观察事件对应节点；
- 在 `MaximumPropagationDepth` 内可到达观察节点的上游祖先节点。

对每个候选，使用有界 BFS 查找候选到观察节点的最短有向传播路径。

### 7.1 解释分数

当前确定性置信度由四部分组成：

```text
Confidence =
  CoverageScore × 0.40
+ TopologyScore × 0.25
+ TemporalScore × 0.20
+ SeverityScore × 0.15
```

- CoverageScore：候选能够解释的活动事件比例；
- TopologyScore：路径深度与边权的综合得分；
- TemporalScore：候选自身事件是否早于下游症状；
- SeverityScore：候选直接健康事件等级；若候选没有直接事件，仅使用下游严重度的一半作为弱推断。

结果按 Confidence、SupportingEventCount、NodeId 确定性排序，并应用 `MinimumCandidateConfidence` 和 `MaximumCandidates`。

该分数是诊断排序分，不是故障概率、SIL、安全等级或自动停机依据。

## 8. 传播路径角色

路径节点标记为：

- RootCause：候选起点；
- Intermediate：因果链中间节点；
- Symptom：活动健康事件对应终点。

每条 `RootCausePropagationPath` 保存：

- TargetEventId / TargetNodeId；
- Depth；
- PathWeight；
- 完整节点序列；
- 完整边序列和关系类型。

## 9. 幂等与不可变快照

`AnalysisId` 使用以下输入计算 SHA-256：

```text
TriggerEventId
+ TriggerEventVersion
+ GraphHash
+ 参与分析的 EventId:Version 集合
```

相同图、相同事件版本和相同 Trigger 会产生相同 AnalysisId。SQL 唯一索引阻止重复写入。

`Wcs_AssetHealthRootCauseAnalysis.AnalysisJson` 保存原始推断快照。人工复核字段单独更新，同时所有复核动作追加写入 `Wcs_AssetHealthRootCauseReviewJournal`，不得覆盖或删除原始候选、路径和解释分数。

## 10. SQL 数据模型

### 10.1 Wcs_AssetHealthRootCauseGraphVersion

保存图版本、Hash、来源、审批和完整图 JSON。

主要索引：

- Version 唯一；
- GraphHash 唯一。

### 10.2 Wcs_AssetHealthRootCauseAnalysis

保存：

- AnalysisId；
- Trigger 事件和版本；
- GraphVersion / GraphHash；
- 时间窗口；
- PrimaryCandidate 摘要；
- 完整 AnalysisJson；
- 当前人工复核摘要。

主要索引：

- AnalysisId 唯一；
- TriggerEventId + Sequence；
- AnalyzedAtUtc。

### 10.3 Wcs_AssetHealthRootCauseReviewJournal

保存每次 Confirmed、Rejected 或 Supplemented：

- ReviewId；
- AnalysisId；
- Decision；
- SelectedRootCauseNodeId；
- Actor；
- Note；
- OccurredAtUtc。

复核 Journal 不因后续复核而覆盖。

## 11. 人工复核语义

| 决策 | 约束 |
|---|---|
| Confirmed | 必须选择推断候选之一；未指定时使用 PrimaryCandidate |
| Rejected | 表示当前推断不成立，不选择根因节点 |
| Supplemented | 必须选择已审批图中的节点并填写说明 |

Supplemented 仅记录现场判断。要将补充关系纳入后续自动推断，必须形成新的图版本，重新完成设备/工艺确认和审批，不能通过 Review API 静默修改活动图。

## 12. API

只读接口：

```text
GET /api/anomaly/root-cause/status
GET /api/anomaly/root-cause/graph
GET /api/anomaly/root-cause/analyses
GET /api/anomaly/root-cause/analyses/{analysisId}
GET /api/anomaly/root-cause/events/{eventId}/latest
GET /api/anomaly/root-cause/analyses/{analysisId}/reviews
```

治理接口：

```text
POST /api/anomaly/root-cause/analyses/{analysisId}/reviews
```

LoadTest 专用：

```text
POST /api/anomaly/root-cause/load/analyses
POST /api/anomaly/root-cause/load/maintain
```

LoadTest Controller 仅在 `LoadTest` 环境返回有效结果，生产不得使用该环境名称。

## 14. 上线顺序

1. 保持 `Enabled=false` 部署；
2. 导入并评审图版本；
3. 离线运行图校验和回放测试；
4. 核对 v3.5 活动事件 AssetId 与 Graph.EntityId；
5. 在隔离环境启用并观察 SQL、内存和分析时延；
6. 人工抽样检查候选和传播路径；
7. 接入项目身份授权；
8. 通过项目变更审批后启用生产只读诊断；
9. 不接入自动停机或调度。

## 15. 监控与故障处理

关注：

- GraphValid、GraphVersion、GraphHash；
- GraphNodes / GraphEdges；
- LastAnalysisUtc / LastError；
- RegisteredGraphs；
- RetainedAnalyses / RetainedReviews；
- SQL 可用性；
- 活动事件数量与分析周期；
- 候选数量、路径深度和低置信结果比例。

常见问题：

- 启用但无分析：检查 v3.5 是否启用、活动事件是否存在、AssetId 是否映射；
- Host 启动失败：检查图审批信息、重复 ID、未知节点、环路和边权；
- 候选过多：缩短时间窗口、降低图范围、提高 MinimumCandidateConfidence；
- 错误传播方向：修正 Upstream → Downstream，而不是调换评分权重；
- Version 冲突：升级图版本，不允许覆盖同版本不同 Hash；
- SQL 异常：关闭 v3.6 或恢复数据库，PLC 和调度继续运行。

## 16. 回退

```text
AssetHealthRootCause__Enabled=false
```

关闭后：

- 停止新的根因分析；
- 保留图版本、分析和复核 Journal 供审计；
- 不影响 v3.5 健康事件、MES Outbox、v3.4 健康历史、Fusion、PLC 或调度。

如需回退图版本，应通过配置发布切换到已审批的旧版本，并保留新旧版本 SQL 记录。

## 17. 当前限制

- 当前算法是确定性图关联，不是贝叶斯因果推断；
- Confidence 不是实际故障概率；
- 未映射实体不会自动猜测节点；
- 人工复核不会自动训练模型；
- 图来源和准确性仍需设备、工艺和实施人员负责；
- 真实现场图、权限、网络、MES 和投产验收属于项目级工作。

## 18. v3.7 接口边界

v3.7 可以读取：

- 原始 v3.5 健康事件；
- v3.6 不可变分析快照；
- Confirmed / Rejected / Supplemented Review Journal。

v3.7 不得覆盖 v3.6 原始推断，也不得把维修建议直接转换为 PLC 或调度命令。
