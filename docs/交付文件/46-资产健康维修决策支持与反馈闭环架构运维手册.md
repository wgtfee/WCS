# 资产健康维修决策支持与反馈闭环架构运维手册

## 1. 文档定位

本文定义 AnomalyEngine v3.7 的规则治理、维修建议、MES 工单关联、人工反馈、效果指标、训练标签候选和运维边界。

v3.7 位于只读诊断与人工决策辅助层：

```text
v3.5 活动健康事件
        +
v3.6 已人工复核根因
        +
已审批维修规则集
        ↓
v3.7 检查建议
        ↓
人工接受 / 拒绝 / 维修 / 无故障 / 误报反馈
        ↓
指标与待审批训练标签候选
```

v3.7 不生成 PLC 命令，不停止设备，不取消任务，不修改路线、路权、车辆选择或派单。

## 2. 生成前置条件

系统只有同时满足以下条件才生成建议：

1. `AssetHealthMaintenance.Enabled=true`；
2. v3.5 事件仍为 Active；
3. v3.6 分析与事件 ID、事件版本一致；
4. v3.6 人工复核结果为 Confirmed 或 Supplemented；
5. Confirmed 根因达到 `MinimumRootCauseConfidence`；
6. 已审批规则集中存在匹配 RootCauseNodeId 或 RootCauseKind 的规则；
7. 事件等级达到规则的 `MinimumEventGrade`。

任何条件不满足均返回无建议，不使用通用文案制造伪建议。

## 3. 规则模型

规则集必须包含：

- Version；
- Source；
- ApprovedBy；
- ApprovedAtUtc；
- Rules。

单条规则支持：

- `RuleId`；
- `RootCauseNodeId` 或 `RootCauseKind`；
- 最低事件等级；
- 标题、优先级、预计分钟数；
- 检查项、部件、工具、备件和安全注意事项。

同一根因同时命中精确节点规则和类型规则时，精确节点规则优先。规则规范化后生成 SHA-256 `RuleSetHash`；同一 Version 不允许注册不同 Hash。

## 4. 建议幂等

`RecommendationId` 由以下字段确定性生成：

```text
RuleSetHash
+ AnalysisId
+ EventId
+ EventVersion
+ RuleId
```

重复扫描、API 重试或 Host 重启不会生成第二条建议。

建议快照保存原始规则内容、根因、置信度、事件等级、维修前健康分和解释。后续反馈只更新生命周期摘要并追加 Journal，不覆盖原始 RecommendationJson、v3.5 事件或 v3.6 分析。

## 5. 生命周期与反馈

建议状态：

```text
Proposed
→ Accepted / Rejected
→ Completed / Cancelled
```

反馈决策：

- Accepted：接受建议，可关联 MES 工单和处理人；
- Rejected：拒绝建议，必须填写原因；
- FalsePositive：确认为误报，必须填写原因；
- Repaired：完成维修，可保存维修后健康分；
- NoFaultFound：现场未发现故障，必须填写原因；
- Cancelled：取消处理。

每次反馈独立保存 FeedbackId、Actor、时间、工单号、处理人、完成时间、维修后健康分和备注。

## 6. MES 工单边界

`MesWorkOrderNo`、`AssignedTo` 和 `CompletedAtUtc` 仅为审计与关联字段。

v3.7 当前不负责自动创建、关闭或审批 MES 工单；不得把 MES 返回结果作为 PLC 联锁、任务状态机或调度决策依据。后续需要主动写入 MES 时，应建立独立 HTTP Outbox 契约和项目级验收。

## 7. SQL 对象

### 7.1 Wcs_AssetHealthMaintenanceRuleSetVersion

保存已审批规则版本、Hash、来源、审批人、审批时间和完整 JSON。

### 7.2 Wcs_AssetHealthMaintenanceRecommendation

保存不可变建议快照及当前生命周期摘要。`RecommendationId` 唯一。

### 7.3 Wcs_AssetHealthMaintenanceFeedbackJournal

保存所有人工反馈。`FeedbackId` 唯一，重复提交幂等。

### 7.4 Wcs_AssetHealthMaintenanceTrainingLabel

保存由 Repaired、FalsePositive、NoFaultFound 形成的候选标签。标签初始状态只能是 PendingApproval。

## 8. 训练标签治理

反馈可以形成：

- `fault-confirmed`；
- `false-positive`；
- `no-fault-found`。

这些记录只是候选标签，必须由独立人员执行 Approved 或 Rejected。批准标签不会自动训练、激活、Canary 或替换现有模型；训练与模型发布继续遵守 v2.1 模型治理流程。

## 9. 指标

状态 API 提供：

- TotalRecommendations；
- AcceptedRecommendations；
- RejectedRecommendations；
- CompletedRecommendations；
- RepairedCount；
- FalsePositiveCount；
- NoFaultFoundCount；
- AcceptanceRate；
- ConfirmedFaultRate；
- FalsePositiveRate；
- AverageClosureMinutes。

样本量较小时不得把比例直接解释为模型质量结论，应结合资产、规则版本、现场和时间范围分层评估。

## 10. API

主要接口：

```text
GET  /api/anomaly/maintenance/status
GET  /api/anomaly/maintenance/rules
GET  /api/anomaly/maintenance/recommendations
GET  /api/anomaly/maintenance/recommendations/{id}
GET  /api/anomaly/maintenance/analyses/{analysisId}/latest
GET  /api/anomaly/maintenance/recommendations/{id}/feedback
POST /api/anomaly/maintenance/recommendations/{id}/feedback
GET  /api/anomaly/maintenance/training-labels
POST /api/anomaly/maintenance/training-labels/{id}/review
```

生产写接口必须接入身份认证、角色授权和审计。Body 中 Actor 仅用于当前无统一认证身份时的兼容场景。

LoadTest 专用接口在非 LoadTest 环境必须返回 404。

## 11. 启用顺序

```text
v3.5 事件治理稳定
→ v3.6 根因分析和人工复核稳定
→ 导入并审批现场维修规则
→ AssetHealthMaintenance.Enabled=true
→ 只读观察建议
→ 验证人工反馈、MES 工单字段和指标
→ 项目级上线签署
```

## 12. 监控

应监控：

- RuleSetVersion、RuleSetHash 和规则数；
- SQL 可用性和 LastError；
- 建议、反馈、待审批标签数量；
- 无规则匹配比例；
- 接受率、误报率、确认故障率和关闭时长；
- 保留期清理结果；
- 身份和权限审计。

## 13. 回退

```text
AssetHealthMaintenance__Enabled=false
```

关闭后停止自动扫描和新增建议，保留规则、建议、反馈和标签审计记录。v3.5、v3.6、PLC、任务和调度继续运行。

不得通过删除 SQL 表、覆盖原始建议 JSON 或自动拒绝待处理建议作为紧急回退手段。

## 14. 安全检查

上线前必须确认：

- Production 默认关闭且 Rules 为空；
- 规则版本、来源和审批完整；
- 无规则时不生成建议；
- Confirmed/Supplemented 之外不生成建议；
- MES 工单字段不触发控制；
- 标签审批不自动更新模型；
- 无 PLC 写入、停机、任务取消或调度修改；
- 现场标准作业、安全要求、工具和备件由专业人员签署。
