# 多模型异常证据融合测试与交付报告

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 功能名称 | AnomalyEngine v3.3 — 多模型异常证据融合 |
| 交付目标 | 统一规则、ML、同群和运输周期异常证据，形成有界、可解释、只读健康状态 |
| 适用分支 | `develop` |
| 默认状态 | `AnomalyFusion:Enabled=false` |
| 安全结论 | 不写 PLC、不停止设备、不改变任务、路权或调度决策 |

## 2. 交付范围

### 2.1 核心实现

- `AnomalyFusionEngine`：同资产、多来源证据融合和状态机；
- `AnomalyEvidenceChannel`：有界异步入口与守恒指标；
- `AnomalyFusionBackgroundService`：异步消费和维护清理；
- `PlcAnomalyFusionBridgeService`：PLC 异常激活/恢复事件桥接；
- `TransportCycleFusionBridgeService`：周期顺序、阶段耗时和总周期异常桥接；
- `AnomalyFusionController`：状态和资产只读 API；
- `AnomalyFusionLoadController`：仅 LoadTest 环境的真实 EventBus 验证入口。

### 2.2 配置和工作流

- `src/Wcs.Host/appsettings.json` 中新增默认关闭的 `AnomalyFusion` 配置；
- `.github/workflows/anomaly-fusion-load.yml`；
- `.github/workflows/anomaly-fusion-bridge-e2e.yml`；
- `.github/workflows/e2e-soak.yml` 增加 GC 后存活内存诊断。

### 2.3 非交付范围

- 自动停止设备；
- 自动取消任务或切换车辆；
- 自动修改 PLC 输出；
- 根因图谱和维修建议；
- 剩余寿命预测；
- 深度学习时序模型。

## 3. 单元测试

融合单元测试覆盖：

1. 同一来源多条 Evidence 只采用最强贡献；
2. 单一高分来源不能独自进入 Alarm；
3. 两个独立来源满足连续评估后进入 Alarm；
4. 全部证据恢复后由维护周期推进正式恢复；
5. 未知 EvidenceId 的恢复事件不能伪造恢复；
6. 活动 Evidence 到期后自动清理；
7. 空闲 Normal 资产自动淘汰；
8. 最大资产容量生效，超限 Evidence 计入 Dropped；
9. 功能关闭时不产生状态。

结果：Fusion 单元测试全部通过，Core、Infrastructure 和 Host Release 编译通过。

## 8. 一小时系统 Soak 与内存验收口径

### 8.1 已发现的问题

一小时工作流最初采用固定并发、无目标速率的闭环请求方式。不同 GitHub Runner 的 CPU 和网络性能会改变实际请求量：

- 一次成功运行约 14,720,872 请求，约 4,089 RPS；
- 后续运行约 24,905,971 请求，约 6,918 RPS，负载提高约 69%。

后一次运行：

- HTTP 失败 0；
- P95 6ms；
- SignalR 错误 0；
- 调度队列峰值/最终 1/0；
- Q4-Q2 36.39 MB；
- 最后 15 分钟斜率 1.662 MB/分钟；
- 但 GC 前 RSS 最终 935.96 MB、峰值 959.23 MB，触发原始固定 RSS 门槛。

该结果说明测试规模随 Runner 漂移，且 GC 前已提交堆不能单独证明仍有对象被引用。Fusion 在该通用 Soak 环境默认关闭，Bridge 状态不是此次 RSS 结果的来源。

### 8.2 修正后的验收方法

工作流保留 GC 前指标和硬上限，同时增加 LoadTest 专用完整 GC 与 LOH 单次压缩：

```text
一小时持续负载
→ 记录初始、季度均值、峰值、最终 RSS 和尾部斜率
→ 验证 HTTP、SignalR、队列和业务证据
→ 状态稳定后执行完整 GC/LOH 压缩
→ 记录 GC 后 RSS 和托管存活内存
```

门槛：

| 项目 | 门槛 |
|---|---:|
| HTTP 失败 | 0 |
| P95 | ≤500ms |
| SignalR 错误 | 0 |
| GC 前 RSS 增长 | ≤900 MB |
| GC 前峰值 RSS | ≤1,200 MB |
| Q4-Q2 | ≤100 MB |
| 最后 15 分钟斜率 | ≤3 MB/分钟 |
| GC 后 RSS 增长 | ≤250 MB |
| GC 后托管存活内存 | ≤256 MB |
| 队列峰值 / 最终 | ≤100 / ≤25 |

调整不是取消峰值限制，而是将“真实泄漏”判定从单一 GC 前 RSS 改为内部状态、趋势和 GC 后存活内存共同判断。

最终发布提交必须对应一条完整成功的一小时工作流；精确运行编号、结果和 Artifact 同步记录在 PR 验收评论中。
