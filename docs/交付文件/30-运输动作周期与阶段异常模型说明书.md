# 运输动作周期与阶段异常模型说明书

## 1. 文档信息

| 项目 | 内容 |
|---|---|
| 功能名称 | AnomalyEngine v3.2 — 运输动作周期与流程阶段模型 |
| 适用分支 | `develop` |
| 核心服务 | `TransportCycleAnalysisService` |
| 执行装饰器 | `ObservedTransportExecutionEngine` |
| 默认状态 | 关闭，`TransportCycleAnalysis:Enabled=false` |
| 数据存储 | 第一版为有界内存记录，不写 PLC、不改变调度状态 |

## 2. 建设目标

规则、Isolation Forest 和同群横向模型主要处理 PLC 信号窗口。v3.2 面向 EMS/RGV 任务完整流程，识别：

- 状态顺序不合法；
- 某个执行阶段明显变慢；
- 整体运输周期明显变长；
- 不同路线或空载、带载任务不能共用同一耗时基线；
- 故障、取消和非法完成记录不能污染正常基线。

模型链路：

```text
ITransportExecutionEngine 调用
→ CoordinatedTransportExecutionEngine 完成真实状态变更
→ ObservedTransportExecutionEngine 比较调用前后快照
→ TransportCycleAnalysisService
→ 阶段轨迹与耗时
→ 路线/载荷上下文
→ Median/MAD 基线
→ 顺序异常、阶段耗时异常、总周期异常
→ 只读 API
```

## 3. 安全边界

1. `CoordinatedTransportExecutionEngine` 仍是唯一负责状态变更的实现。
2. 周期模型不修改任务、车辆、路权、PLC 命令或调度决策。
3. 模型异常不会自动暂停或停止设备。
4. 默认关闭时装饰器直接调用原执行引擎，不读取前置快照，不增加周期状态。
5. 所有内存集合均有容量上限。
6. `Faulted`、`Cancelled` 和非法顺序的 `Completed` 周期只用于审计，不进入正常耗时基线。

## 4. 周期阶段

模型跟踪以下执行状态：

- `Assigned`；
- `MovingToPickup`；
- `Loading`；
- `MovingToDestination`；
- `Unloading`；
- `WaitingForRoute`；
- `Paused`；
- `Completed`；
- `Faulted`；
- `Cancelled`。

同状态位置反馈只更新时间，不切分新阶段。例如车辆在 `MovingToDestination` 中连续上报多个位置，不会产生多个移动阶段。

阶段记录包含：

| 字段 | 说明 |
|---|---|
| State | 阶段状态 |
| EnteredAtUtc | 进入时间 |
| ExitedAtUtc | 离开时间 |
| DurationMilliseconds | 阶段耗时 |
| Occurrence | 同一状态在本周期中的出现次数 |

等待路权和暂停后恢复可能使同一状态多次出现。基线分析会按状态汇总同一周期内的总耗时。

## 5. 顺序校验

模型按执行状态机允许的迁移关系校验顺序，例如：

```text
Assigned
→ MovingToPickup
→ Loading
→ MovingToDestination
→ Unloading
→ Completed
```

以下属于异常示例：

```text
Assigned → Completed
Loading → Completed
Completed → MovingToDestination
```

检测到非法迁移时生成 `InvalidSequence` 记录，并将整个周期标记为 `IsSequenceValid=false`。即使终态为 `Completed`，该周期也不会进入正常基线。

## 6. 终止周期

以下状态结束当前周期：

- `Completed`；
- `Faulted`；
- `Cancelled`。

故障重分配通过同一个 `ObservedTransportExecutionEngine` 观察。故障后再次取消或重复提交终态操作，不会产生第二条周期，也不会留下跟踪状态。

## 7. 上下文基线

当前上下文键由任务路径和载荷类型组成：

```text
Path=<Source>><Pickup>><Destination>|Load=<EMPTY/LOADED>
```

因此：

- 不同目的地不共用基线；
- 空载和带载不共用基线；
- 同一路线、同载荷任务才能进行历史耗时比较。

后续版本可在不改变周期模型主体的情况下加入任务类型、产品、班次和设备类型等上下文。

## 8. Median/MAD 耗时检测

只有合法完成周期进入基线。

每个上下文分别保存最近 `MaximumBaselineCyclesPerContext` 条正常周期，并计算：

```text
Median = 历史耗时中位数
MAD = |历史耗时 - Median| 的中位数
稳健尺度 = max(MAD × 1.4826, MinimumMadMilliseconds)
偏离度 = max(0, (当前耗时 - Median) / 稳健尺度)
```

满足以下条件时判定为慢周期或慢阶段：

```text
历史周期数 >= MinimumBaselineCycles
当前耗时 > Median
偏离度 >= MadMultiplier
```

模型只检测“变慢”，不会把异常快的周期直接定义为故障。

## 9. 异常类型

### 9.1 InvalidSequence

记录状态顺序错误，包括前状态、后状态、操作名称和操作结果。

### 9.2 PhaseDuration

某一阶段总耗时偏离同上下文历史基线。

示例：

```text
MovingToDestination 实际 1000ms
历史中位数 300ms
稳健尺度 10ms
偏离 70
```

### 9.3 TotalDuration

完整周期总耗时偏离同上下文历史基线。

## 10. 配置

```json
{
  "TransportCycleAnalysis": {
    "Enabled": false,
    "MinimumBaselineCycles": 30,
    "MaximumBaselineCyclesPerContext": 500,
    "MaximumTrackedExecutions": 20000,
    "MaximumCompletedCycles": 5000,
    "MaximumAnomalies": 5000,
    "MadMultiplier": 6.0,
    "MinimumMadMilliseconds": 100.0,
    "MinimumTotalDurationMilliseconds": 0,
    "MinimumPhaseDurationMilliseconds": 0
  }
}
```

| 参数 | 说明 | 建议 |
|---|---|---|
| Enabled | 周期分析总开关 | 现场先在测试环境开启 |
| MinimumBaselineCycles | 开始检测前的最少正常周期 | 30～100 起步 |
| MaximumBaselineCyclesPerContext | 每个路线/载荷上下文基线容量 | 根据路线数量与内存压测 |
| MaximumTrackedExecutions | 最大并行跟踪任务数 | 大于系统最大在途任务数 |
| MaximumCompletedCycles | API 保留的最近周期数 | 按审计需求设置 |
| MaximumAnomalies | API 保留的最近异常数 | 按运维需求设置 |
| MadMultiplier | 慢周期偏离门槛 | 6～10 起步 |
| MinimumMadMilliseconds | 稳健尺度下限 | 防止历史耗时完全一致导致过敏 |
| MinimumTotalDurationMilliseconds | 总周期最低检测耗时 | 可过滤极短任务 |
| MinimumPhaseDurationMilliseconds | 阶段最低检测耗时 | 可过滤毫秒级阶段 |

## 11. API

### 11.1 状态

```http
GET /api/transport/cycle-analysis/status
```

主要指标：

- `TrackedExecutions`；
- `CompletedCycles`；
- `BaselineContexts`；
- `ObservedTransitions`；
- `SuccessfulCycles`；
- `InterruptedCycles`；
- `InvalidSequenceAnomalies`；
- `DurationAnomalies`；
- `DroppedExecutions`。

### 11.2 最近周期

```http
GET /api/transport/cycle-analysis/cycles?maxCount=200
```

### 11.3 最近异常

```http
GET /api/transport/cycle-analysis/anomalies?maxCount=200
```

### 11.4 LoadTest 专用入口

```http
POST /api/transport/cycle-analysis/load/scenario
```

仅 `LoadTest` 环境可用，其他环境返回 404。该入口只向周期服务注入确定性快照，不修改真实调度或 PLC。

### 12.1 单元测试

已覆盖：

- 正常周期阶段轨迹；
- 同状态反馈不重复切阶段；
- 非法完成不进入基线；
- 故障周期不进入基线；
- 不同路径上下文隔离；
- 正常基线建立后识别慢阶段和慢总周期；
- 直接 `Start` 保留 `Assigned` 阶段；

- 终态后重复操作不产生重复周期；

## 13. 投产建议

```text
Enabled=false
→ 测试环境开启并观察周期轨迹
→ 核对路径和载荷上下文
→ 积累不少于 MinimumBaselineCycles 的正常周期
→ 分析阶段耗时分布
→ 调整 MinimumMadMilliseconds 和 MadMultiplier
→ 只读告警展示
→ 人工确认
→ 再考虑持久化、治理和 AlarmCenter 集成
```

第一版不建议直接用于自动停机或自动重新调度。

## 14. 当前限制与下一阶段

当前版本：

- 周期和异常保存在有界内存中；
- 没有 SQL 生命周期表；
- 没有人工复核和 Shadow/Canary 发布；
- 没有自动根因传播；
- 上下文仅包含路径和载荷；
- 不估算剩余寿命。

下一阶段将把规则、Isolation Forest、同群偏离和周期异常统一到多模型融合层，输出统一设备/任务健康证据和置信度，再进入根因关联分析。
